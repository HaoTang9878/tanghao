# 读书笔记

> 读书是为了思考，思考是为了成长 —— 把书本读薄，把认知变厚

下面是我读过的三本技术经典的真实笔记与读后感，每本都反复翻阅，记录下真正影响我写代码方式的洞察。

## 《重构：改善既有代码的设计》—— Martin Fowler

这是让我"看代码的眼光发生质变"的一本书。Fowler 的核心主张不是教你怎么写新代码，而是怎么在不改变外部行为的前提下，让既有代码更易读、更易改。

### 坏味道总结

书中最实用的部分是"代码坏味道"清单。我把它们归纳为三大类：

1. **命名与结构类**：神秘命名（名字不能表达意图）、过长函数（一个函数塞了太多职责）、过大的类（一个类管太多事）、过长参数列表（参数多到调用方记不住）。这些问题的共同根源是"一个抽象层里混入了太多细节"。
2. **重复与耦合类**：重复代码（散落各处的相同逻辑）、发散式变化（一个类因多种原因被改）、霰弹式修改（一个改动要动多个类）、依恋情结（函数对别的类兴趣超过自己的类）。这类味道的本质是"职责归属错位"。
3. **数据与抽象类**：数据泥团（总是一起出现的数据项没被封装成对象）、基本类型偏执（用字符串、数字表达本该是对象的电话号、金额）。这类味道提醒我们"数据缺少行为的封装"。

识别坏味道是第一步，真正难的是克制住"全部推翻重写"的冲动——Fowler 反复强调：重写是最后的手段，渐进式重构才是常态。

### 核心重构原则

- **小步重构，频繁测试**：每一步改动都应小到可以立即验证。把大重构拆成几十个原子提交，随时可回退。
- **测试是重构的前提**：没有测试的重构如同蒙眼走钢丝。重构前先补齐安全网，哪怕只是特征测试（characterization test）。
- **行为不变是底线**：重构不改变外部可观察行为，任何"顺手优化逻辑"的念头都要单独拆出来做。

### 印象深刻的手法

- **提取函数**：用得最多。把长函数里一段有内聚性的逻辑抽成独立函数，用意图命名。做完这一步，原函数往往就成了一篇"读得懂的故事"。
- **引入参数对象**：把总是一起出现的参数（起止日期、经纬度）封装成对象，调用瞬间清爽，也消除了数据泥团。
- **以多态取代条件表达式**：用子类多态替代 switch-on-type，是消除发散式变化的利器。

## 《代码整洁之道》—— Robert C. Martin

Uncle Bob 这本书的主旨可以浓缩成一句：代码是写给人看的，只是顺便能让机器执行。它教会我在"能跑"之上，追求"能读"。

### 命名规则

命名是这本书着墨最多的主题，也是最被低估的功夫。核心原则：

- **名字要回答"是什么"而非"怎么做"**：`getDaysBetween` 比 `calc` 好，`activeUsers` 比 `data` 好。避免 `d1`、`temp`、`info` 这类需要上下文才能理解的名字。
- **避免误导**：`accountList` 如果不是 List 类型就是误导；用 `accounts` 更安全。
- **有意义的区分**：`product` 与 `productInfo`、`productData` 之间的区别无人能辨，等于没有区分。
- **动词与名词的搭配**：方法名用动词或动宾结构（`saveUser`、`calculateTotal`），布尔返回用 `is`/`has`/`can` 前缀（`isReady`、`hasPermission`）。

### 函数原则

- **短小**：函数应尽量短，理想情况下不超过 20 行。理由不是行数本身，而是短小函数更容易做到单一职责。
- **单一职责**：一个函数只做一件事。判断标准：能否把其中一部分提取成独立的、有意义的函数——如果能，就该提取。
- **参数越少越好**：零参数最好，三个以上几乎总有办法封装成对象。布尔参数往往意味着函数做了两件事，应该拆成两个函数。
- **无副作用**：函数名承诺做的事之外，不要悄悄改了全局状态或参数。`checkPassword` 里不该顺带初始化会话。

### 注释哲学

这本书对注释的态度出人意料地"消极"，但细想很有道理：

- **好代码胜过好注释**：当代码能自解释时，注释反而是维护负担——代码改了注释忘改，比没注释更糟。
- **注释该解释"为什么"，而非"做什么"**：`i++; // i 加 1` 是噪音；`// 这里减 1 是因为索引从 0 开始，而接口约定从 1` 才有价值。
- **法律、意图、警示类注释值得保留**：版权声明、设计决策的背景、对潜在陷阱的提醒，这些是代码无法承载的信息。

## 《深入理解计算机系统》（CSAPP）—— Randal E. Bryant

CSAPP 是少有的能"把硬件和软件打通"的书。它从程序员的视角出发，讲清楚了一段高级代码在机器层面到底发生了什么。读完最大的收获是：很多"玄学"的性能问题与 bug，底层都有可解释的机制。

### 程序的机器级表示

这一章让我第一次真正理解了 C 代码如何映射到汇编。关键认知：

- **寄存器是稀缺资源**：x86-64 只有 16 个通用寄存器，函数调用要靠栈传递溢出的参数与局部变量。这解释了为什么递归过深会爆栈——每层调用都消耗栈空间。
- **汇编与高级代码的对应**：`if`/`while` 在汇编里都是条件跳转（`je`、`jne`、`jl`），循环本质是带跳转的条件判断。理解这一点，才能看懂编译器优化的边界。
- **缓冲区溢出的根源**：C 不做边界检查，数组写越界直接覆盖相邻内存——栈上的返回地址被覆盖，就是经典的栈溢出攻击原理。

### 内存层次结构

这一章把"为什么内存访问性能差异巨大"讲透了：

- **金字塔结构**：寄存器 → L1 → L2 → L3 → 主存 → 磁盘，每层容量更大但速度更慢，差着几个数量级。
- **局部性是性能关键**：时间局部性（最近访问的再访问）和空间局部性（连续地址会被预取到 cache）。这就是为什么按行遍历二维数组比按列快——前者利用了 cache 行的预取，后者不断 cache miss。
- **学会用局部性思维写代码**：把热点数据紧凑存放、循环嵌套时把大循环放内层，都是利用 cache 友好性的实战技巧。

### 链接

链接这一章解答了我多年的疑惑——"为什么编译能过却链接报错"：

- **符号解析**：链接器要为每个外部符号找到定义。未定义引用（undefined reference）本质是某个符号在所有目标文件与库中都没找到定义。
- **静态库与静态链接**：链接器按命令行顺序处理库，且只提取当前已引用的符号。这解释了为什么库的顺序很重要——被依赖的库要放在依赖它的库之后。
- **重定位**：链接器合并各目标文件的段，并为每个符号分配最终运行时地址，再修正所有引用这些地址的指令。理解重定位，才能真正懂"全局变量地址在编译期未知、运行期才确定"。

CSAPP 的价值在于它把"写代码"从黑盒变成了白盒：当程序出问题时，你能顺着调用栈一路追到机器级，而不是停留在"它就是不对"的困惑里。
